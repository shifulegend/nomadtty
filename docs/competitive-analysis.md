# NomadTTY — Competitive & Adoption-Readiness Analysis
<!-- Human/product-facing report — not part of docs/ai/'s AI-agent memory tree. -->
<!-- Prepared: 2026-07-30 -->

This report evaluates NomadTTY the way an outside adopter would evaluate any
closed-source tool before deploying it: install friction, configuration
ergonomics, first-time hosting difficulty, documentation/help quality, and
how it stacks up against established Linux remote-terminal tools and the
top GitHub repos in this space. It closes with a prioritized backlog of
recommended changes (not implemented here — this is analysis only).

Findings below combine direct repository inspection (this session) with
external web research on comparator tools; every external claim about a
named competitor cites a source, and unverifiable live numbers (GitHub star
counts, etc.) are flagged as approximate.

## Executive summary

NomadTTY's differentiators are real and largely uncontested: a mobile
touch-toolbar that fixes a documented, unfixed upstream xterm.js gap every
competitor inherits, and a 10-tool MCP server giving AI agents authenticated,
persistent-session terminal access — no other web-terminal project combines
both. Its biggest weakness is self-inflicted, not competitive: **two parallel
deployment models that were never reconciled.** The legacy `install.sh` path
is a genuinely good one-command installer; the newer Session Manager + MCP
architecture — the one actually running production — has no installer, no
Docker/compose wiring, and a systemd unit that requires hand-editing.
Configuration is env-var-only with no wizard anywhere, and the one required
secret (`MCP_AUTH_TOKEN`) is entirely hand-generated by the operator.
Documentation is otherwise a strength (README, community-health files) with
two cheap, specific gaps: no `--help`/`--version` output anywhere, and no
`CHANGELOG.md`.

## Methodology

Each area below (A–F) corresponds to a question posed by the project owner,
answered as if reviewing NomadTTY as a prospective adopter with no access to
its source history or internal docs — only what a real operator would
encounter (README, install scripts, running the app) plus how comparable
tools handle the same problem.

## A — Installation benchmarking

| Tool | Install command | Steps/decisions | Single artifact? | Reverse-proxy/TLS/persistence |
|---|---|---|---|---|
| **NomadTTY (legacy)** | `curl -fsSL .../install.sh \| sudo bash` | 1 command, 0 prompts (env-var configured) | Yes | HTTP-only nginx vhost; systemd unit auto-written/enabled; no TLS by default |
| **NomadTTY (Session Manager + MCP)** | `git clone`; `npm install`; `MCP_AUTH_TOKEN=$(openssl rand -hex 32) node server/main.js` by hand | Multiple manual steps, no wizard | **No** — no installer/Dockerfile/compose wiring at all | Systemd unit exists but hardcodes one host's paths/user; operator must hand-author the `EnvironmentFile` — nothing generates it |
| Tailscale | `curl -fsSL https://tailscale.com/install.sh \| sh && sudo tailscale up` | 2 commands, 1 browser SSO step | Yes, script detects distro itself | N/A (no local web UI); systemd unit auto-enabled |
| Pi-hole | `curl -sSL https://install.pi-hole.net \| bash` | 1 command, launches an interactive `whiptail` wizard (~6-8 prompts) | Yes | Own admin UI bundled; systemd services enabled automatically |
| Portainer | `docker run -d ... portainer/portainer-ce:latest` | 1 command + first-run web wizard | Yes, single container | Self-signed HTTPS built in; `--restart=always` |
| netdata | `sh netdata-kickstart.sh` | 1 command, non-interactive | Yes | systemd auto-enabled; no TLS by default |
| Cockpit | `apt-get install cockpit && systemctl enable --now cockpit.socket` | 2 commands | Yes, native package | Self-signed HTTPS + socket activation built in |
| Coolify | `curl -fsSL .../install.sh \| bash` + web registration | 1 command + web step | Yes | Ships Traefik + automatic Let's Encrypt for everything it deploys — strongest of this set |
| ttyd (upstream) | apt PPA or build from source | Multiple manual steps, no wizard, no systemd unit shipped | No | Fully DIY |

Sources: [tailscale.com/docs/install/linux](https://tailscale.com/docs/install/linux), [pi-hole/pi-hole basic-install.sh](https://github.com/pi-hole/pi-hole/blob/master/automated%20install/basic-install.sh), [Portainer install docs](https://docs.portainer.io/start/install-ce/server/docker/linux), [netdata kickstart.sh](https://github.com/netdata/netdata/blob/master/packaging/installer/kickstart.sh), [cockpit-project.org/running](https://cockpit-project.org/running), [Coolify installation docs](https://coolify.io/docs/get-started/installation), [ttyd](https://tsl0922.github.io/ttyd/).

**Verdict:** The legacy installer ranks **average-to-strong** — directly
comparable to netdata's kickstart.sh, better than Pi-hole's on raw friction,
behind Cockpit/Portainer/Coolify only on automatic TLS. The Session
Manager + MCP path — the one actually in production — ranks **weak**, on par
with raw upstream ttyd's DIY build experience. Every comparator ends in one
coherent, repeatable "day one" path; NomadTTY's two models don't reconcile,
and the one running in production is the unpackaged one.

## B — Configuration & wizard ergonomics

| Tool | First-run experience | Secret handling | Unified config? |
|---|---|---|---|
| **NomadTTY** | None — env vars only, no wizard in either model | 100% operator-generated (`openssl rand -hex 32`, pasted by hand) | No — two disjoint env-var surfaces (3 vars legacy, ~15 vars Session Manager/MCP), no config file |
| Home Assistant | Full web onboarding wizard (create account, set location, auto device discovery) | User-chosen via GUI form | Yes, GUI-driven |
| Portainer | Web setup wizard on first launch | `setup_token` **machine-generated**, printed to logs; admin password operator-chosen | Yes, GUI-driven |
| Nextcloud | 3-step browser wizard w/ password-strength meter | Operator-chosen via GUI | Yes |
| Pi-hole | Terminal (`whiptail`) wizard at install time | Admin password auto-generated by installer | Yes, wizard-driven |
| Caddy | None needed — near-zero config, auto HTTPS | N/A | Yes, one Caddyfile |
| Cockpit | None needed — reads/writes real OS state directly | N/A | N/A |
| Tailscale | `tailscale up` opens a browser OAuth login; `--auth-key` for automation | Auth keys mintable via API, not `openssl`-by-hand | Yes |

Sources: [home-assistant.io/getting-started](https://www.home-assistant.io/getting-started/), [docs.portainer.io/start/install/server/setup](https://docs.portainer.io/start/install/server/setup), [docs.portainer.io/advanced/cli](https://docs.portainer.io/advanced/cli), [nextcloud web-installer](https://github.com/nextcloud/web-installer), [docs.nextcloud.com installation_wizard](https://docs.nextcloud.com/server/latest/admin_manual/installation/installation_wizard.html), [pi-hole basic-install.sh](https://github.com/pi-hole/pi-hole/blob/master/automated%20install/basic-install.sh), [Caddy zero-config guide](https://kx.cloudingenium.com/en/caddy-reverse-proxy-automatic-https-zero-config-guide/), [cockpit-project.org](https://cockpit-project.org/), [tailscale.com/docs/features/access-control/auth-keys](https://tailscale.com/docs/features/access-control/auth-keys).

**Verdict: weak.** Every comparator gives the operator either a guided
wizard, a genuinely zero-touch safe default, or a machine-generated/managed
secret. NomadTTY has none of these. **Highest-value fix:** an installer/setup
script that auto-generates `MCP_AUTH_TOKEN` when unset, writes it into a
`chmod 600` env file, and prints it once — mirroring Portainer's
machine-generated `setup_token` pattern, at far lower cost than a full GUI
wizard.

## C — First-time hosting ease

Restating from A/B with a hosting-specific lens: the legacy model gets a new
operator from zero to a browser-accessible terminal in one command and under
a minute (apt installs + a health-check curl). The Session Manager + MCP
model — which is what a real deployment actually wants, since it's the
architecture running production and the one with AI-agent/MCP support — has
no equivalent: `npm install`, manually exporting `MCP_AUTH_TOKEN`, manually
running `node server/main.js` in a terminal that must stay attached (or
hand-adapting the systemd template for persistence). A first-time host who
wants the *complete*, currently-recommended feature set (mobile toolbar +
multi-session + MCP) cannot do so with a single command today; they must
combine both models by hand, with no documentation walking them through that
specific combination.

## D — Documentation & help best practices

- **GNU Coding Standards** treat `--help`/`--version` as baseline, not
  optional, CLI UX ([gnu.org/prep/standards](https://www.gnu.org/prep/standards/html_node/Command_002dLine-Interfaces.html)).
  NomadTTY has **zero** runtime `--help`/`--version` output from any
  entrypoint (`install.sh`, `server/main.js`) — confirmed by code inspection,
  not assumption.
- Well-regarded CLIs (ripgrep's two-tier `-h`/`--help`, `gh`'s per-subcommand
  help plus a dedicated `environment` command, Docker's recursive
  `Usage:`/`Options:` blocks) all treat help text as a first-class,
  machine-checkable artifact ([ripgrep guide](https://iepathos.github.io/ripgrep/common-options/), [gh manual](https://cli.github.com/manual/gh_help_reference), [Docker CLI reference](https://docs.docker.com/reference/cli/docker/)).
- The **Diátaxis** framework (tutorial/how-to/reference/explanation) shows
  NomadTTY's README-only approach covers reference and how-to well but is
  thin on tutorial/explanation — a normal, low-urgency limitation of
  README-only docs generally ([diataxis.fr](https://diataxis.fr/)).
- **CHANGELOG.md** (Keep a Changelog format) is common but not universal in
  this tier — neither Uptime Kuma nor Portainer ships one either, both using
  GitHub Releases instead ([keepachangelog.com](https://keepachangelog.com/en/1.1.0/), [uptime-kuma](https://github.com/louislam/uptime-kuma), [portainer](https://github.com/portainer/portainer)). NomadTTY's absence of one is a
  "nice, common, not disqualifying" gap.
- **In-product help** in this tier is lightweight by convention (Uptime
  Kuma's empty-state CTA, Portainer's field-level tooltips), not heavyweight
  product tours ([Uptime Kuma guide](https://www.xda-developers.com/uptime-kuma-guide/), [Portainer release notes](https://docs.portainer.io/sts/release-notes)). NomadTTY's single
  empty-state string is directionally right but under-elaborated versus
  these comparators.

**Verdict: average**, pulled down by two specific, cheap fixes rather than
weak reference docs — NomadTTY's README + full community-health file set
(CONTRIBUTING/SECURITY/CODE_OF_CONDUCT/SUPPORT/issue templates/CODEOWNERS/
Dependabot) is arguably above the Uptime Kuma/Portainer baseline already.

## E/F — Competitive landscape (top Linux tools & top GitHub repos)

| Tool | Mobile/touch UX | Session persistence | AI-agent/MCP integration | Auth model | Popularity/activity |
|---|---|---|---|---|---|
| **NomadTTY** | Purpose-built toolbar: sticky Ctrl/Shift/Alt, F-keys, pinch-zoom safety, keyboard-aware resize | tmux, native | **Yes** — 10-tool MCP server, bearer-token auth | ttyd loopback-only + MCP bearer token | New project (this repo) |
| ttyd (tsl0922/ttyd) | None built-in | None (external tmux needed) | No | Optional HTTP basic auth / SSL | ~12.1k★, actively maintained ([repo](https://github.com/tsl0922/ttyd)) |
| GoTTY (yudai/gotty) | None | None | No | Basic auth only | ~19.5k★ but effectively unmaintained ([issue #258](https://github.com/yudai/gotty/issues/258)) |
| Wetty | None | SSH reconnect, no multiplexer | No | SSH login / `--ssh-auth` | ~5.3k★, no release since 2023, still gets issues ([repo](https://github.com/butlerx/wetty)) |
| Shellinabox | None | None | No | Basic auth / PAM | ~3.1k★ community fork, maintenance ask open ([issue #531](https://github.com/shellinabox/shellinabox/issues/531)) |
| sshwifty | None | Client-side reconnect only | No | Server-defined presets, no accounts | ~2.9-3.1k★, active releases ([repo](https://github.com/nirui/sshwifty)) |
| WebSSH2 | None | None | No | HTTP Basic → SSH, debated weak auth UX | ~2.8k★, actively maintained ([repo](https://github.com/billchurch/webssh2)) |
| tmate | N/A (tmux fork) | Native, via relay | No | Possession of generated URL | ~6.1k★, active ([tmate.io](https://tmate.io/)) |
| Cockpit | Terminal tab reported "nearly unusable" on phones | Rides host PAM session | No | PAM/SSO/certs — most mature auth here | Red Hat-backed, large, active ([mobile issue #18138](https://github.com/cockpit-project/cockpit/issues/18138)) |
| code-server | Full VS Code UI, not phone-optimized | Long-running server process | No | Password or none; **no built-in multi-user support** | ~77.8k★, very active ([discussion #6253](https://github.com/coder/code-server/discussions/6253)) |

Underlying cause of the shared mobile weakness: every one of these embeds
xterm.js, which has a standing, unresolved upstream issue on mobile touch
usability ([xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)); none ship a fix layer on top.

**MCP/AI-agent integration search:** no mainstream web-terminal project
above has native MCP support. Two narrow adjacents exist — `tmux-mcp`
([nickgnd/tmux-mcp](https://github.com/nickgnd/tmux-mcp)) and
`libtmux-mcp` — but with no web/mobile front end at all. The closest analog,
`terminal-control-mcp` ([wehnsdaefflae/terminal-control-mcp](https://github.com/wehnsdaefflae/terminal-control-mcp)),
combines tmux + an optional xterm.js viewer but has **no authentication
system** and no mobile design (≈12★, unverified).

**Verdict:** NomadTTY's two differentiators — a real mobile toolbar fixing a
documented xterm.js gap, and authenticated MCP-based AI-agent access to a
persistent session — are essentially uncontested. Where competitors lead:
Cockpit and code-server have far more mature auth/access-control (PAM/SSO/
OIDC vs. one bearer token) and mature install ecosystems; code-server dwarfs
everyone in scale/ecosystem; none of the pure web-terminal tools offer real
multi-user isolation, and NomadTTY's named-session model doesn't fully close
that gap either.

## G — Prioritized backlog of recommended changes

Backlog only — nothing below has been implemented in this session.

### Install / deployment unification (highest impact)
1. **Give the Session Manager + MCP path an actual installer** — at minimum
   a `docker run`/compose one-liner or an `install.sh`-equivalent that runs
   `npm install`, generates `MCP_AUTH_TOKEN`, and starts `server/main.js` —
   closing the single biggest gap versus every comparator surveyed.
2. **Template and install the `systemd/nomadtty.service` unit** the same way
   `install.sh` already templates `systemd/ttyd.service` (parameterized
   paths/user), instead of requiring hand-editing for each host.
3. **Reconcile the two deployment models long-term** so a fresh install
   yields the full, currently-recommended feature set (mobile toolbar +
   multi-session + MCP) via one path — the two-model split is itself the
   clearest outlier versus every tool surveyed.
4. Add automatic TLS to the legacy nginx path (Certbot or an embedded
   reverse proxy), matching Cockpit/Portainer/Coolify's out-of-the-box HTTPS.

### Configuration & secrets (highest value-to-effort ratio)
5. **Auto-generate and store `MCP_AUTH_TOKEN`** in an installer/setup script
   (`openssl rand -hex 32`, written to a `chmod 600` env file, printed once)
   instead of requiring the operator to run the command by hand — mirrors
   Portainer's machine-generated `setup_token` pattern at low implementation
   cost.
6. Consider a single `.env`/config-file mechanism shared by both deployment
   models, reducing the current two disjoint env-var surfaces (3 vars vs.
   ~15 vars) to one.

### Documentation & help (cheap, specific)
7. **Add `--help`/`--version` output** to `install.sh` and `server/main.js`
   — a GNU-standards baseline every comparator CLI meets; currently a
   confirmed hard zero, not just undocumented.
8. Add `CHANGELOG.md` (Keep a Changelog format) — common in this tier though
   not universal (GitHub Releases is an acceptable substitute if preferred).
9. Add a small number of contextual tooltips/richer empty-state guidance in
   the Session Manager UI, matching the lightweight pattern used by Uptime
   Kuma/Portainer (not a full onboarding tour).

### Product/UX (longer-term)
10. Evaluate real multi-user access control (distinct from named sessions)
    if multi-tenant use is a goal — the gap versus Cockpit/code-server.
11. Revisit TLS/reverse-proxy defaults for the legacy model, since every
    top-tier comparator (Cockpit, Portainer, Coolify) ships HTTPS by
    default rather than leaving it entirely to the operator.
